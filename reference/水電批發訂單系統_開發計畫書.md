# 水電材料批發訂單管理系統 — 開發計畫書

> 本文件供 Claude Code 作為專案開發指引使用，涵蓋第一階段（中秋節前上線）與第二階段（優化期）。

---

## 一、專案概述

**客戶背景**：水電材料批發商，現行以 LINE 接單＋紙本＋Excel 對帳，人工依賴度高，曾發生對帳爭議。

**核心目標**：
- 內部（老闆、兒子、工讀生）可用系統管理訂單、庫存、對帳
- 部分客戶可自行透過網頁下單
- 中秋節前（約 1 個月）上線可用版本

**技術棧**：
- Backend + 管理端：Laravel（最新穩定版 12.x）+ Vue 3
- 客戶端：RWD 網頁，與後台共用同一 Laravel 專案（不做原生 App）
- Database：開發使用 SQLite 後續上線使用MySQL 8.x
- 通知：LINE Messaging API（官方帳號 + webhook，非 LINE Notify，該服務已於 2025 年廢止）
- PDF 產生：dompdf 或 mpdf（Laravel 套件生態）
- Excel 匯出：maatwebsite/excel (Laravel Excel)

---

## 二、共用架構原則

**一套後端、兩個前端**，避免訂單/庫存邏輯分裂成兩套：

```
共用後端 API
  ├── 內部管理端（完整功能，兒子/工讀生/老闆使用）
  └── 客戶端（陽春版，僅：LINE Login、下單、老樣子、查詢自己訂單）
```

客戶端權限嚴格限制在自己的資料範圍內，不可觸及庫存管理、預留邏輯設定、對帳報表。

## 三、第一階段：中秋節前上線（MVP）

### 3.1 範圍
- 內部管理端：完整功能
- 客戶端：陽春版（能用即可，不追求體驗）
- 通知：LINE Messaging API（App 內推播延後到第二階段，因不做原生 App）

### 3.2 資料庫設計（Migration 規劃）

| Table | 說明 |
|---|---|
| `products` | 商品主檔（約 20-30 種品項） |
| `product_variants` | 規格（每品項 5-6 種尺寸/規格） |
| `inventory` | 庫存數量，含「預留額度」欄位 |
| `customers` | 客戶主檔，含月結/貨到付款屬性、LINE User ID |
| `reservations` | 熟客預留額度紀錄，含到期時間 |
| `orders` | 訂單主檔，含狀態（待確認/已確認/已出貨/已失效） |
| `order_items` | 訂單明細 |
| `payments` | 付款紀錄，含付款方式（匯款/現金/支票）、已收/未收狀態 |
| `recurring_order_templates` | 客戶自訂的「常用訂單」範本（供老樣子功能參照，若採最近N筆則此表可省略，改為直接查詢 orders） |
| `notifications_log` | LINE / 站內通知發送紀錄 |

> 決策點：老樣子功能已定案為「列出最近 5-10 筆歷史訂單」，故不需要額外的常用組合設定表，直接查詢該客戶最近的 `orders` 即可，減少開發量。

### 3.3 功能模組與執行步驟

**Step 1：環境建置與資料庫設計**
- 建立 Laravel 專案、設定 MySQL 連線
- 撰寫所有 migrations、seeders（測試資料）
- 建立基礎的 Model 關聯

**Step 2：商品與庫存模組**
- 商品/規格 CRUD（內部管理端）
- 庫存扣減邏輯（出貨時扣減，需考慮並發鎖定，避免同時搶貨造成超賣）
- 熟客預留額度機制：
  - 設定每位客戶的預留規則（頻率、預留量）
  - Scheduled Job：檢查預留是否到期，到期未確認則釋放額度
  - 到期前 7 天觸發提醒（見 Step 5）

**Step 3：訂單管理模組（內部端）**
- 建單、改單、訂單狀態流轉
- 老樣子查詢 API：回傳該客戶最近 5-10 筆訂單供選擇
- 工讀生／兒子可代客戶下單

**Step 4：付款與對帳模組**
- 付款狀態標記（已收/未收，付款方式）
- 月結客戶：月底彙總報表
- Excel 匯出（Laravel Excel）

**Step 5：LINE Messaging API 串接**
- 引導客戶申請 LINE 官方帳號（此步驟需客戶端配合，非純開發工作，需提前排入時程）
- Webhook 接收客戶訊息（可選：僅用於推播，不做雙向對話機器人，降低複雜度）
- 推播情境：
  - 預留額度到期前 7 天提醒
  - 訂單確認通知

**Step 6：PDF 訂單產生**
- 下單當下即產生 PDF（含商品明細、金額、匯款帳號資訊）
- 補印功能（重新產生同一份 PDF）

**Step 7：客戶端（陽春版）**
- LINE Login 串接（免密碼，降低使用門檻）
- 下單頁面（選品項、數量）
- 老樣子選單（最近 5-10 筆）
- 查詢自己的訂單狀態、付款狀態

**Step 8：測試與試用支援**
- 找 2-3 位熟客先行試用
- 蒐集回饋、修正明顯的操作問題

**Step 9：部署上線**
- 主機與網域設定
- 正式環境資料庫遷移

### 3.4 明確排除於第一階段
- 進貨/供應商管理系統化
- 客戶端「常用組合自訂」（已定案改為最近N筆）
- 定期訂單自動產生（已定案改為提醒＋手動確認）
- 原生 App 通知（無原生 App）
- 多倉庫管理
- 正式發票/稅務系統串接

## 四、第二階段：優化期（中秋節後）

### 4.1 範圍
- 客戶端體驗優化（介面、操作流程簡化）
- 依第一階段試用回饋調整功能
- 視需求評估是否要做原生 App（若客戶端使用率高且客戶反映需要推播體驗更好）

### 4.2 待評估項目（依第一階段回饋決定優先順序）
- 客戶端 UI/UX 優化
- 若確定不做原生 App，評估 Web Push Notification 作為 App 內通知的替代方案
- 進貨管理模組（若阿明認為有需要系統化）
- 對帳報表視覺化（目前僅 Excel 匯出，可評估加入圖表儀表板）
- 客戶端「常用組合」功能（若試用後發現年輕客戶有需求，再評估加入）

## 五、Claude Code 執行時建議的 Skill 使用

依專案性質，開發階段建議依序使用以下能力：

- **後端/資料庫**：一般程式撰寫能力即可，重點在 migration 設計與並發鎖定邏輯（庫存扣減）需特別小心測試
- **PDF 產生**：若需要在本機測試/驗證產出的 PDF 格式，可搭配 `pdf` skill 檢視產出結果
- **Excel 匯出**：若需要驗證匯出的 Excel 格式是否正確可讀，可搭配 `xlsx` skill 開啟確認
- **前端 Vue / RWD 頁面**：若涉及介面設計調整，建議搭配 `frontend-design` skill 確保客戶端（陽春版）介面在手機上仍有基本可用性，而非純技術堆砌
- **文件輸出**：完成後的 README、API 文件建議用 `docx` skill 產出正式文件版本（若客戶或協作者需要 Word 格式），一般開發過程紀錄則用 Markdown 即可

> 注意：LINE 官方帳號申請、Messaging API 金鑰設定屬於帳號層級操作，需要客戶（阿明）本人或授權人員配合完成，Claude Code 僅能協助程式串接與 webhook 邏輯撰寫。
